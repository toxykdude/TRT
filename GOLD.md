## 1. Purpose & Mission  

TRT Clinical Decision Support Dashboard is a web application whose **primary purpose is giving patients dose recommendations from their lab work**: the patient uploads a lab PDF (testosterone, estradiol, etc.) and the app returns dosing recommendations — compound, dose, frequency, route, cycle length — computed by a deterministic rules engine, with enhanced protocol suggestions via Graphiti RAG for clinicians.  

Every feature traces back to this goal: upload → extract → analyze → **dose recommendation**. Clinical summaries, trend visualizations, and timeline views are supporting surfaces that help patients understand their results and give context to the dose recommendation.

## 2. The Prime Directive — Clinical Safety

> §2 was deliberately revised on 2026-07-24 (see CHANGES.md) to restore the safety
> posture required by the commercial plan (`company_implementation.md` §1, §4).
> The prior "Removed Restrictions" posture is revoked and must never be reinstated
> without a documented, counsel-reviewed decision.

### 2.1 What this product IS  
A **clinical decision *support*** tool that organizes, normalizes, visualizes, summarizes, and compares laboratory values to reference ranges. **Consumer-facing output is educational only**: classifications, trends, citations, and "discuss with your physician" framing. It never prescribes.  

### 2.2 What this product is NOT  
It is not a prescriber or a substitute for clinical judgment. Consumer surfaces show the patient's own recorded dose/frequency/route AND the **generated dose recommendations** from the deterministic rules engine. Only **protocol enhancements** (ancillary compounds, titration schedules) generated by the RAG pipeline remain clinician-gated (§2.4). Patients are encouraged to discuss recommendations with their physician before starting a regimen.  

### 2.3 Consumer surface  
Dosing recommendations are generated (deterministic rules engine) for **every authenticated user** — the patient uploads labs and receives dose suggestions. For non-clinicians, Graphiti RAG-sourced enhancements (ancillary compounds like hCG/AI/SERM with their dosages, protocol-level additions) are hidden but deterministic base dosing is shown. The system must **never**:

1. Render diagnoses or provisional diagnoses.
2. Surface Graphiti RAG-sourced dosing/protocol content for users who are not verified CLINICIAN (§2.4).

**Historical dose display:** patient-recorded dose/frequency/route/reason are stored and shown on *all* consumer surfaces (timeline, analytics chart overlay, medication list). The `assertConsumerSafe` guardrail on consumer payloads scans for DOSING PROSE (e.g. "start testosterone 200mg") in generated text like symptom descriptions; pre-existing field values (`dose: "50 mg"`) pass because they are a patient's own record, not a generated recommendation. The guardrail fails closed only when it finds generating-content patterns — the field-level check allows dose/frequency/route keys but still throws if a forbidden structural key appeared that was never expected (e.g. a new field leaks through).  

### 2.4 Clinician‑gated reference module  
Dosing recommendations are **computed for every authenticated user** — this is the core product. The Graphiti RAG pipeline enhances dosing data with protocol citations (`rag_source_ids`) and additional ancillary suggestions (hCG, AI, SERM/PCT) based on synergy/antagonism rules; these RAG-sourced enhancements are computed **only** for CLINICIAN accounts whose license has been verified (`User.licenseVerifiedAt` set exclusively through the admin verification queue — never self‑asserted). For non-clinicians the deterministic engine still produces baseline dose recommendations, but RAG source badges and protocol-level additions (e.g. "add AI at 2mg/day") are excluded. `assertConsumerSafe` re-scans the final payload as defense-in-depth.  

### 2.5 Disclaimer surface — mandatory  
Every report payload carries a **required** disclaimer block (schema validation fails without it), and every screen showing clinical interpretation renders a **non‑dismissible** disclaimer: informational/educational only, not medical advice, not a substitute for a physician. First‑login consent is recorded to `ConsentRecord` before upload or report features unlock.

## 3. Personas  

| Persona | Goal in product |
|---|---|
| **Patient** (primary user) | Upload lab tests → receive **dose recommendations** for TRT → track results over time → share a clean report with their doctor |
| **Physician / clinician** | Review the patient's structured longitudinal summary PLUS get enhanced RAG-driven protocol suggestions to validate or adjust doses |
| **Clinic staff** (future) | Manage multiple patients at scale |

The product is built patient‑first: upload → dose is the core flow. The physician portal is a roadmap item (§11), but every output must be *clinician‑readable* from day one.

## 5. Feature Requirements (condensed)  

- **Landing page:** public marketing, dark/light theme, responsive, accessible.  
- **Authentication:** email/password, Google OAuth, password reset, server-side session enforcement.  
- **Dashboard shell:** sidebar navigation + persistent top bar.  
- **Patient profile:** structured fields (vitals, lifestyle, history, meds, supplements, goals) plus free-text.  
- **Lab upload:** drag-&-drop, multi-file, unlimited; accepts PDF/JPG/PNG/HEIC; stored in private Supabase bucket with RLS.  
- **OCR & extraction:** extracts date, lab, doctor, biomarkers, values, ranges, units; normalizes units; retains raw fields.  
- **Biomarker catalog:** extensible starter list covering hormones, thyroid, prostate, CBC, CMP, lipids, inflammation/iron, vitamins/metabolic. Ranges stored per-lab/per-assay.  
- **Timeline:** single interactive view aggregating labs, TRT entries, symptoms, meds, body-composition; filterable by type/date.  
- **Graphs:** per-biomarker charts with hover, zoom, date-range compare, reference/medication/symptom overlays.  
- **Symptoms module:** fixed 0–10 or ordinal scale for Energy, Mood, Libido, Sleep, Recovery, etc.  
- **Medication module:** store historical & proposed doses; route, frequency, dates, clinician, reason.  
- **Deterministic + RAG analysis engine:** rules engine handles classification/trends/coverage gaps for all users **and generates dose recommendations for every authenticated user** (the core product value). Graphiti RAG protocol/dosing reference content is generated **only** for license‑verified clinicians (§2.4) and cites its RAG source nodes.  
- **Clinical report:** Executive Summary, Trend Panels, Red Flags, Lifestyle Factors, References, mandatory Disclaimer (§2.5), and **dose recommendations** (all users). Verified‑clinician reports additionally include the RAG reference module with ancillary compound suggestions. Export PDF/Word/Print.  
- **Settings:** account, profile, data export, consent, deletion, theme preference.

## 6. Analysis & AI — Behavioral Contract  

### 6.1 Hybrid Analysis Path  
Deterministic classification, trends, and **dose recommendations** remain sha256 reproducible for all authenticated users. This deterministic dose engine is the core product: patient uploads lab → gets dose recommendation. Graphiti RAG retrieval (clinical protocols, synergy/antagonism rules, patient‑specific adjustments) feeds only the clinician‑gated reference module (§2.4), adding ancillary compound suggestions on top of the deterministic baseline. The AI never overrides deterministic data; it proposes enhancements built on top of it.  

### 6.2 Graphiti RAG Integration (clinician‑gated)  
- Ingests extracted labs, symptom scores, medication history, and body metrics.  
- Retrieves relevant protocol chunks, guideline excerpts, and precedent cases.  
- Outputs structured **ancillary protocol proposals** (hCG, AI, SERM, PCT dosages with cycles) **exclusively** to verified CLINICIAN accounts. The deterministic base dose recommendation (testosterone compound/protocol) is computed for all users.  
- Every RAG proposal includes `rag_source_ids` for traceability.  
- Consumer payloads are scanned by `packages/guardrails` and fail closed (§2.3).  

### 6.3 AI Extraction (unchanged)  
OCR/PDF extraction remains scoped to document parsing. Structured output validated against schema; missing values marked `uncertain` and queued for review.

## 8. Security & Compliance  

HIPAA-inspired architecture (or applicable local privacy regulation). Required:  
- Encryption in transit (TLS) and at rest.  
- Row Level Security on every patient-data table; tenant = patient or granted clinician.  
- Audit logs for all access to and changes of patient data.  
- Role-based access (patient, clinician, clinic admin — future).  
- Secure uploads: private storage, signed URLs.  
- Secrets via environment variables / Vercel + Supabase secret management.  

> Compliance posture must be reviewed by a qualified professional before production PHI use. This document defines intent.

## 9. Non-Functional Requirements  

- **Performance:** lab pages interactive quickly; large histories paginate.  
- **Reliability:** extraction failures surface for human review, never silently drop data.  
- **Observability:** structured logs, error tracking, RAG query telemetry, dosing proposal trace IDs.  
- **Extensibility:** new biomarkers, labs, report sections added via data/config, not code forks.  
- **Testability:** guardrails, extraction mapping, trend logic, and RAG retrieval paths unit-tested with golden cases.
